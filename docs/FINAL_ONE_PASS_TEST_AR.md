# SecureShop Café — الاختبار النهائي في جولة واحدة

## قبل التجربة
1. أوقفي الموقع (`Control+C`) وخدي نسخة كاملة من `~/Desktop/SecureShop_Cafe_v2` وخاصة `secureshop.db`.
2. من الـZIP الجديد **انقلي ملفات الكود والاختبارات والمستندات فقط** للمشروع الحالي. لا تستبدلي `secureshop.db` ولا `.venv`.
3. شغلي:
   ```bash
   cd ~/Desktop/SecureShop_Cafe_v2
   source .venv/bin/activate
   python -m pip install -r requirements.txt
   python -m unittest discover -s tests -v
   python app.py
   ```
4. افتحي `http://localhost:8000`؛ استخدمي العنوان نفسه لتسجيل Passkey والتحقق منها، وتجنبي 127.0.0.1 في الواجهة.

**جميع المدفوعات برصيد تجريبي.** لا تستخدمي كلمات مرور حقيقية ولا تشاركي QR أو OTP أو Cookies في Screenshots.

## النوافذ
- Chrome عادي: User تجريبي، `/login`.
- Chrome Incognito: `admin@example.test` مع الباسورد المسجل لديكي، `/login` ثم `/admin`. بعد تفعيل MFA، كود الحساب الصحيح من تطبيق Authenticator.

## Blue Team — Typing Behavior Authentication
1. ادخلي بحساب تجربة، ثم `/account` → **Security settings: typing and passkeys** → **Enroll typing rhythm**.
2. اكتبي **باسورد حسابك التجريبي نفسه** خمس مرات، كل مرة في صفحة النموذج واضغطي Save trusted sample. **اكتبيه بيدك، لا تعملي Paste أو Autofill.**
3. المفروض يظهر `5/5` و`Ready` في `/security`.
4. اعملي Logout ثم Login بصورة طبيعية، وبعدها قارني مع محاولة كتابة بطيئة جدًا في جلسة أخرى. راجعي Audit Log من Admin لحدث `behavior_anomaly` إن ظهر.
5. الـz-score حدّه 3.0. **توقيت المتصفح قابل للتزوير**؛ لا يعتبر إثبات هوية، ولذلك الموقع يعتمد على الباسورد وMFA كعوامل تحقق حقيقية. هذا التنفيذ يستخدم signal للرصد وليس وحده سببًا لإعطاء دخول.

## Blue Team — Passkey, Location and Time Security
1. **التسجيل**: من `/security` اكتبي باسورد الحساب، ثم **Register this device passkey**. وافقي على Passkey من النظام أو جهازك. المتصفح لازم يدعم WebAuthn؛ مفيش رقم أو Signature بيتم إدخاله يدويًا.
2. اتأكدي إن `Registered passkeys` اتغير بعد Refresh.
3. **الاختبار**: اضغطي `Run security risk assessment`، ووافقي على WebAuthn وعلى Location.
4. السيرفر يتحقق من توقيع ES256 ومن RP ID / Origin / Challenge، وبعدها المسافة من **نقطة تجريبية ثابتة: القاهرة 30.0444, 31.2357** بحد 50 كم، والساعة بتوقيت القاهرة من 08:00 شاملة إلى 22:00 غير شاملة. لذلك **بعد 22:00 طبيعي يظهر BLOCK (time)**.
5. تجربة انتقالية فقط: لو عايزة تفعّلي بوابة Location and time policy عند Login للحسابات المسجّل لها Passkey، اقفلي السيرفر وشغليه بـ:
   ```bash
   SECURESHOP_RISK_GATE_ENFORCE=1 python app.py
   ```
   بعد الباسورد (+ TOTP لو مفعّل) هتظهر صفحة Passkey/Location/Time قبل اكتمال الدخول. **متفعليش السياسة دي لكل الحسابات أثناء الاستخدام العادي**؛ لأنها بتمنع الدخول خارج الساعات أو لو صلاحية الموقع مرفوضة. لو دخلتي في Lockout وقت التجربة، أوقفي السيرفر وشغّليه من غير المتغير (بيانات الحساب تفضل محفوظة).
6. لا يُعتبر Geolocation المرسَل من المتصفح إثبات موقع موثوق؛ المستخدم يقدر يزوّره، وده Demo policy مطابق لافتراض Location and time policy مش Production-grade geofencing.
7. WebAuthn backend في النسخة تعليمي: يدعم ES256/P-256 و`none attestation` على localhost فقط. بعض أجهزة Passkey قد تستخدم تنسيقًا مختلفًا؛ في الحالة دي التطبيق يرفض التسجيل ولا يتخطى التحقق.

## Security regressions (اختبار من التطبيق المحلي فقط)
| ID | تجربة | النتيجة |
|---|---|---|
| S01 | قيمة سعر مزيفة من واجهة العميل | السيرفر يعتمد على قاعدة البيانات |
| S02 | استعمال نفس الكوبون للمستخدم مرتين | يرفض الاستخدام الثاني |
| S03 | كميات سالبة/كبيرة ومخزون صفر | يرفض أو يتعامل بأمان بدون خصومات زائفة |
| S04 | Checkout بسلة فارغة أو رصيد قليل | يرفض بدون إنشاء طلب أو سحب رصيد |
| S05 | User يفتح Order يخص User مختلف | 404 / رفض |
| S06 | User يفتح Admin أو Audit | 403 |
| S07 | OTP غلط أو مكرر | رفض |
| S08 | CSRF Token مفقود في POST | 403 |
| S09 | نص HTML في Display name | يظهر كنص ولا يُنفَّذ |
| S10 | Session/Logout وأحداث Audit | جلسة غير صالحة لا تعرض صفحة محمية |
| S11 | Passkey بتوقيع أو Challenge خاطئ | رفض |
| S12 | Location risk خارج 50كم أو 22:00 | BLOCK في البوابة الاختيارية |

سجلي لكل حالة: `ID`, التاريخ، الدور، خطواتك، **Actual Result**, Pass/Fail، وصورة **من غير أسرار**.

## آخر خطوة
شغلي `python -m unittest discover -s tests -v` واحتفظي بسطر `Ran ... tests` و`OK`. النتيجة اللي ظهرت داخل بيئة بناء النسخة: **42 tests, OK** في بيئة منفصلة. تسجيل Passkey ظهر ناجحًا على Mac في محادثة سابقة، لكن يلزم إعادة تجربة السيناريو النهائي بعد استبدال الكود، مع تسجيل الأدلة.
